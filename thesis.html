This system is an IoT-based Ornamental Fish Counter and Inventory Management System running on a Raspberry Pi 5. It uses a YOLO-based camera detection model to count fish crossing a virtual line in real-time, and a React web dashboard for inventory management. The database is MariaDB (InnoDB) optimized for low-resource edge deployment.

6 Database Design Evaluation

✅ Strengths

  • ✓ InnoDB engine — ACID transactions, row-level locking
  • ✓ utf8mb4 charset — full Unicode support throughout
  • ✓ Soft deletes — inventory.deleted preserves data for recovery
  • ✓ Singleton pattern — counting_state id=1 is clean for global flags
  • ✓ Composite index — idx_device_time on readings is optimal for time-series
  • ✓ bcrypt auth — industry-standard token hashing in devices
  • ✓ Lightweight runtime — only 4 tables deployed, minimal RPi overhead
  • ✓ Reasonably normalized — 2NF-3NF, acceptable denormalization for variant

⚠️ Issues Found

  • ⚠ Missing index — inventory (deleted, action) not in live DB
  • ⚠ VARCHAR vs ENUM — action is VARCHAR(32), allows invalid values
  • ⚠ Negative counts — wholesale deductions use count = -100, no CHECK constraint
  • ⚠ No variant lookup — variant is free-text, typos create phantom variants
  • ⚠ Schema gap — 8 planned tables not deployed (by design)

📐 Normalization Assessment

Normal FormStatusNotes
1NF ✓ Met All columns are atomic, no repeating groups
2NF ✓ Met No partial dependencies — all non-key attributes depend on the full primary key
3NF ✓ Mostly Met variant as inline VARCHAR vs. a lookup table is an acceptable pragmatic denormalization for a 3-variant system

7 Problems & Risks

🔴 Duplicate Entry Risk
The /save_inventory endpoint has no idempotency check. Double-clicking "Save" or retried network requests can insert the same fish count twice.
Fix: Add a unique constraint on a request fingerprint, or implement application-level debounce with a cooldown window.
🟠 Inconsistent Count Convention
IN records use positive counts. OUT records use positive counts (interpreted as subtracted). But WHOLESALE deductions use negative counts (-100). This mixed-sign convention complicates aggregation queries.
Fix: Standardize all counts as positive values — let the action column determine the direction.
🟠 Missing Constraints
  • No CHECK on inventory.count to prevent zero values
  • action is VARCHAR(32) — should be ENUM('IN','OUT','WHOLESALE')
  • No unique constraint or validation on variant names
🔵 Stale Counting State (Mitigated)
If fish_counter.py crashes, counting_state.active stays 1. However, the system already has crash recovery: startup_clear_stale_state() checks the PID file on boot and resets the flag. ✅ Already handled.

9 Defense-Ready Explanations

❓ "Why are some tables empty?"

The system was designed with a scalable multi-device architecture in mind, where multiple Raspberry Pi cameras could report to a central server. Tables like devices and readings support this multi-node deployment, including secure device authentication with bcrypt-hashed tokens and raw telemetry logging.

In our current thesis deployment, we use a single Raspberry Pi 5 where the camera and server run on the same device. In this configuration, fish counts flow directly from the YOLO detection module into the inventory table through the web dashboard, so the device registry and raw readings pipeline are not activated.

These tables are structurally ready and will be populated when the system scales to multiple cameras.

❓ "How does the database support the system?"

The database plays three critical roles:

1. Real-time control — The counting_state table acts as a global switch that the web dashboard uses to start and stop the YOLO detection process. It includes crash recovery: if the detection process crashes, the system automatically resets this flag on restart.

2. Inventory management — The inventory table records every stock movement with the action type (IN, OUT, WHOLESALE), fish variant (Platinum, Black, Pineapple), count, date, and notes. This supports the dashboard's stock summary, sales trends, and analytics views. Soft deletes preserve data integrity.

3. Scalable telemetry — The devices and readings tables form a secure IoT data pipeline with bearer-token authentication and indexed time-series storage, ready for multi-camera deployment.

❓ "Why was this design chosen?"

We chose MariaDB on InnoDB for several reasons:

• ACID transactions ensure inventory counts are never partially written, even during power failures on the Raspberry Pi.
• Row-level locking allows the detection module and web dashboard to write simultaneously without blocking each other.
• Lightweight footprint — with only 4 active tables and tuned buffer settings (128 MB), the database runs efficiently within the RPi 5's resource constraints.
• Phased design — we designed the full schema with 12 tables covering users, roles, suppliers, purchase orders, OTA firmware updates, calibrations, audit logs, and notifications. We deployed only the 4 tables needed for the thesis prototype, following a pragmatic approach: "build what you need now, design for what you'll need later." This demonstrates system extensibility without overcomplicating the prototype.
